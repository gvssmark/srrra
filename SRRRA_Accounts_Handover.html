1. What this app is

A small accounting system for IBRA covering double-entry Journal data entry, a chart of Accounts, and reporting (Ledger, Balance Sheet & Income/Expenditure, an Accounts summary), plus an end-of-year closing workflow. It replaced a set of manually maintained Google Sheets — one per financial year — with a single continuous Journal and Accounts sheet, entered through a small installable web app instead of typing directly into cells.

It was built incrementally through conversation with Claude, evolving from "add a data-entry form to my spreadsheet" into a full multi-view Progressive Web App (PWA) with reporting, PDF export, and a year-end closing procedure.

2. Architecture

Three layers, deliberately kept simple — no database, no server you have to manage:

Google Sheet data store
Four tabs: Journal, Accounts, BSIEcodes, Settings. This is the single source of truth.
↕ read / write via Apps Script
Apps Script Web App Code.gs
Deployed as a Web App (a public /exec URL). Exposes a small JSON API (doGet/doPost) that the frontend calls. Runs "as Me" (the Sheet owner), so it can read/write the Sheet regardless of who is using the app.
↕ fetch() over HTTPS
Static PWA index.html on GitHub Pages
A single-page app — no build step, no framework, no npm install. Plain HTML/CSS/JS in one file, hosted as a static site. This is what people actually open on their phones.
Why this shape? No server to pay for or maintain, no login system to build, and anyone with basic Apps Script/GitHub access can maintain it. The trade-off is discussed in Section 9 — there's no real access control.

3. The Google Sheet

Journal — line-item schema (one row per Dr or Cr line)

This schema changed after the app's first version The original design was one row per transaction, with separate drAccount/crAccount columns — that only supports a simple 1-debit/1-credit transaction. To support batch/compound transactions (e.g. several expense claims paid out via a couple of cheques that don't match 1:1), the schema was changed to a line-item model: every row is a single line (one account, one amount, tagged Dr or Cr), and a "voucher" is a group of rows sharing the same jrnlNo. See Section 4 for how this works and how existing data was migrated.
ColumnMeaning
dateTransaction date — shared by every line in a voucher
jrnlNoThe voucher number. Resets to 1 at the start of each financial year. Multiple rows sharing a jrnlNo form one voucher. Duplicates within a year are tolerated; corrected manually if needed.
accountFull account name (e.g. 1004-BANK ACCOUNT NO 465693063), must match an entry in Accounts exactly
drCrExactly Dr or Cr — which side of this line's account this amount hits
detailsFree-text narration for this line
amountThis line's amount
finYeare.g. 2025-26. This is what all reporting filters on — the Journal is one continuous sheet across all years, not one file per year.

A simple transaction is a 2-line voucher (1 Dr line + 1 Cr line, same amount) — this is what the "Journal" menu produces. A batch/compound transaction is a voucher with more lines, where only the totals must balance (sum of Dr lines = sum of Cr lines for that jrnlNo) — not each line paired 1:1 against a specific contra account. This is what the "Batch Transactions" menu produces.

This sheet is the authoritative source for how the Balance Sheet & Income/Expenditure report is structured — every code present here shows as a line on the report, even with a zero balance, matching how the original manually-maintained spreadsheet looked.

Two codes are load-bearing, not decorative 2-05 (Liabilities) and 1-07 (Assets) are used by the app as computed surplus/deficit "plug" lines — the app writes into these automatically at report time so the Balance Sheet balances. Deleting them will break the balance check. Similarly 3-10 and 4-06 are the equivalent plug lines on the Income & Expenditure statement.

4. Backend — Code.gs

Migrating from the old schema

Code.gs includes a one-time function, migrateJournalToLineItems(), meant to be run manually from the Apps Script editor (not exposed via the Web App). It reads the old-format Journal, writes the converted line-item rows into a new sheet called Journal_NEW — leaving the original untouched — and the administrator then renames the sheets to swap them in once satisfied. Full step-by-step is in README.md Section 4.

Batch Transactions (multi-line vouchers)

submitBatchJournal(entry) takes {date, finYear, lines: [{account, drCr, details, amount}, ...]}, validates at least one Dr line and one Cr line, validates every account exists, validates the Dr total equals the Cr total, then writes all lines as one atomic batch (a single setValues() call) sharing one new jrnlNo. The simple submitJournalEntry(entry) (used by the "Journal" menu) is really just a 2-line special case of the same underlying model, written directly rather than routed through the batch function.

A single Apps Script file deployed as a Web App. It has no database of its own — every call reads the Sheet fresh, computes what's needed, and (for writes) appends rows. Key design points:

Sign convention

Matches standard double-entry accounting, inferred from the original spreadsheet's numbers: Asset and Payment (expenditure) accounts are debit-normal (balance = totalDebits − totalCredits); Liability and Receipt (income) accounts are credit-normal (balance = totalCredits − totalDebits).

Per-financial-year scoping

Even though the Journal is one continuous sheet, every report (Ledger, BSIE, Accounts Report) filters strictly to the selected finYear. This reproduces what the old per-year spreadsheet files showed, because the opening-balance entry for each year is itself a normal Journal row dated 1 July of that year.

Journal numbering

jrnlNo is computed as "highest existing number for this finYear, plus one" — scoped per year, not a global running count. It resets to 1 automatically each time a new financial year starts (there's no explicit "reset" step; it falls out naturally from the per-year scoping).

Financial Year Closing

Two-step: previewCloseFinancialYear(finYear) (read-only — computes what would be posted) and closeFinancialYear(finYear, passcode) (writes it). It posts one voucher (one shared jrnlNo): every non-zero Asset balance becomes a Dr line, every non-zero Liability balance (other than the B/f account itself) becomes a Cr line, and the account mapped to BSIE code 2-01 takes whichever side balances the voucher — dated 1 July of the next FY. Payment/Receipt (nominal) accounts are not carried forward — they start the new year at zero simply because the Journal filter excludes prior years. It refuses to run if the next FY already has any entries, to prevent duplicate opening balances. Because this voucher naturally has many lines, it reads as "Batch / Sundries" in the Ledger, same as any other batch entry.

Admin passcode & data-entry access control

Stored as an Apps Script Script Property named ADMIN_PASSCODE — not in the code itself, so it survives redeployments and can be changed without touching Code.gs. Originally this only gated Financial Year Closing; it now also gates every Journal, Batch Transactions, and Account Addition write — see Section 9 for how the unlock flow works. There's still no other in-app admin function by design — deleting a Journal entry, purging old years, or editing Accounts is done directly in the Sheet.

Reusing this codebase for a second organization

Because organization identity lives in the Settings sheet (Section 3), not in code, a second organization needs no code changes: a new Google Sheet with the same four tabs, a fresh Apps Script deployment (new /exec URL — each Sheet needs its own), and a copy of index.html with only its WEB_APP_URL line changed. The one exception is manifest.json/icon.svg — static files fetched before any app code runs, so the home-screen name/icon still need a one-line manual edit per deployment. Full steps are in README.md Section 5.

5. Frontend — index.html

A single static HTML file — no build tools, no bundler. It's a hand-rolled single-page app:

  • Hash-based router (#journal, #bsie?fy=2025-26, etc.) — a plain object mapping route names to render functions.
  • Hamburger nav with six views: About/Dos&Don'ts (default landing page), Journal, Account Addition, BSIE Reports, Ledger Reports, Accounts Report, Financial Year Closing.
  • Custom autocomplete for the Journal's Debit/Credit account fields — filters as you type against the loaded account list, rather than a plain dropdown.
  • All data comes from the Apps Script Web App via fetch(). POST requests deliberately use Content-Type: text/plain (not application/json) — this avoids a CORS preflight request that Apps Script Web Apps don't handle, while the server still parses the body as JSON.

One config line at the top of the <script> block — const WEB_APP_URL = '...' — points the whole frontend at your Apps Script deployment. This is the one thing that must be updated whenever the Apps Script deployment URL changes.

6. PDF report generation

This went through two approaches worth knowing about, because the first one's failure shaped the final design:

Attempt 1 — html2canvas + jsPDF's doc.html() (abandoned)

The first approach rendered the on-screen report by screenshotting the live DOM (html2canvas) and embedding that image into a PDF. In practice this produced clipped columns, cut-off text, and garbled/duplicated content at page breaks on the multi-column BSIE statement — html2canvas doesn't reliably handle complex CSS table layouts, especially the side-by-side two-statement table this report needed.

Attempt 2 — jsPDF + jspdf-autotable (current, working)

The current approach draws the PDF programmatically — real vector text, lines, and cells via doc.autoTable(...) — instead of rasterizing the page. There's no "container width" to get wrong and nothing to clip, because every cell is placed explicitly. It also produces genuinely selectable/searchable text, which the screenshot approach never could.

Design note for future reports Any new PDF report added to this project (or any future project) should follow this same pattern — jsPDF + jspdf-autotable, drawing tables directly, not screenshotting a rendered page. This is saved as a standing preference in the account that built this app; if you're working from a different Claude account, it's worth stating this preference yourself early on (see Section 12).

Reports each go through a small shared toolkit of helper functions in index.html:

  • pdfSectionTitleBar_() — draws the black title bars (e.g. "ASSETS AND LIABILITIES AS ON 30/06/2026")
  • pdfTwoColStatement_() — draws two tables side-by-side with a shared start Y, so their Total rows land on the same line without relying on matching row heights
  • pdfSignatories_() — draws the President / General Secretary / Treasurer / Auditor signature line block used at the end of BSIE and Ledger reports

"Save PDF" always downloads the file. "Share via WhatsApp" only appears when the browser genuinely supports attaching a file via the Web Share API (navigator.canShare({files:...})) — a real file gets attached, not just a link; on browsers without that support the button is hidden entirely rather than offering a broken experience.

7. PWA packaging

manifest.json and sw.js make the app installable to a phone's home screen. The service worker is intentionally minimal — it caches the app shell (HTML/CSS/JS/icon) for fast loading, but it does not queue offline Journal submissions. Data entry and reports still require an internet connection to actually reach the Apps Script backend.

8. Deployment & redeployment

Full step-by-step is in README.md alongside the code; the short version:

  1. Google Sheet has the four tabs with exact header rows (Section 3).
  2. Code.gs pasted into Extensions > Apps Script, ADMIN_PASSCODE set as a Script Property, deployed as a Web App (Execute as: Me, Who has access: Anyone).
  3. WEB_APP_URL in index.html updated to that deployment's /exec URL.
  4. index.html, manifest.json, icon.svg, sw.js pushed together to a GitHub repo with Pages enabled.

To change backend code later: Deploy > Manage deployments > edit the existing deployment > New version > Deploy. This keeps the same /exec URL, so index.html doesn't need updating.
To change frontend code: just push the updated index.html to GitHub — no redeploy step needed on the Apps Script side.

9. Security & access model

There is still no per-person login system — but data entry is now passcode-gated. Reports (About, BSIE, Ledger, Accounts Report) are open to anyone with the link, with no passcode. Journal, Batch Transactions, Account Addition, and Financial Year Closing all require the same ADMIN_PASSCODE. This is still a shared-secret model, not real authentication — it was a deliberate trade-off, consistent with keeping this a small-committee tool rather than building full auth.
  • How the unlock works: in the nav menu, the four data-entry items are hidden behind a data-protected="1" attribute until unlocked. A "🔒 Unlock Data Entry" link prompts for the passcode, verifies it via the non-throwing checkPasscode GET action, and on success stores the passcode itself in the browser's localStorage (key entryPasscode) — this is what makes the unlock persist across visits rather than needing re-entry every session.
  • Enforced server-side, not just hidden client-side: doPost in Code.gs calls checkPasscode_() before submitJournalEntry, submitBatchJournal, or submitAccountEntry run — a direct API call without the right passcode is rejected regardless of what the UI shows.
  • If a stored passcode is later rejected (e.g. an admin rotates ADMIN_PASSCODE), the frontend's handleWriteError_() detects the "Incorrect passcode" message, clears the stored value, and re-locks that device automatically.
  • ADMIN_PASSCODE is a plain Script Property — visible to anyone with edit access to the Apps Script project — so treat it as a shared PIN, not a real secret. Route guarding in the frontend router also blocks direct hash navigation (e.g. typing #journal in the URL bar) to a protected view while locked.
  • No in-app delete, purge, or account-editing UI exists by design — those are handled by an administrator editing the Google Sheet directly.
  • Journal numbers can duplicate if two people submit around the same moment — accepted as fine, correctable manually in the Sheet if it ever matters.

10. Known limitations

  • No page-number auto-counting in printed reports — browsers don't reliably support this without extra tooling; the Ledger's running header shows the report label and generation date instead.
  • No offline write queueing (see Section 7).
  • "Share via WhatsApp" depends on browser support for file-sharing via the Web Share API — mainly Chrome on Android today. It degrades gracefully (button simply doesn't appear) elsewhere.
  • The BSIEcodes sheet's 2-05/1-07/3-10/4-06 codes are structurally required for the balance-check plug logic (Section 3) — removing them will break report balancing, not just cosmetics.
  • Dates display as dd/mm/yyyy and numbers use Indian lakh/crore grouping ('en-IN' locale) throughout reports — this is deliberate, not a bug, and hardcoded rather than a user-configurable setting.
  • The Ledger's "Batch Transactions Summary" page only appears when viewing All Accounts, and only in the printed/PDF output as a genuinely separate page — it's a normal (non-paginated) section when viewed on screen.

12. Continuing development with Claude

To pick up development, a new administrator just needs to:

  1. Open a new conversation with Claude (any Claude account/plan that supports file uploads and artifacts works).
  2. Upload the current Code.gs, index.html, and this handover document for context.
  3. Describe the change wanted — Claude can read the existing code and extend it in the same patterns described above (e.g. add a new report by following the same doGet action + vector PDF builder pattern used for the Accounts Report).
Memory does not transfer between Claude accounts The "always use jsPDF + jspdf-autotable for PDF reports, never screenshot-based generation" preference was saved in the previous administrator's Claude account memory. A new administrator using their own account won't have that context automatically — it's worth restating it explicitly in the first conversation (or asking Claude to save it to their own memory, if that feature is enabled for their account) so future PDF work follows the same reliable pattern rather than re-discovering the same screenshot-clipping problem from scratch.
